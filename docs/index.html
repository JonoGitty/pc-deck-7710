What this is

A deck is what a head unit is called. This one started on a PC and grew into the real thing.

The PC deck — working

A Pioneer-style faceplate in a browser, fed by whatever your PC is playing. Spectrum analyser, VU needles, album art, synced lyrics, dolphins when the music stops. This is what most people run.

The car deck — renderer done, firmware not

ESP32 and an OLED or VFD panel, Bluetooth audio from your phone, into a standard DIN cage. The renderer is finished and verified, and the firmware is written and compiles — A2DP, metadata, the analyser, both panels, movies and diagnostics. It has never run on hardware, and this site will say so until it has.

Everything on this page was rendered by the code in the repository. The screen animations come out of the same C the firmware links; the faceplate photographs are the real page in a real browser with the WebSocket stubbed. There are no mockups here, and one command regenerates the lot — which is the only way a page like this stays true a year from now.

The movies

Animations you make yourself, in pure Python — no GPU, no Blender.

They play on the PC deck and on the hardware. Same file, same decoder, same dots. Each of these solves a different version of one problem: four brightness levels is not many.

Making one is a conversation, not a tutorial. The repository carries a CLAUDE.md that tells Claude the constraints — the right grid for your panel, the level budget, why thin bright details dither into noise on 1-bit glass, why large areas must sit on a level centre. Describe the animation you want and which display you have; it picks the format.

Try it now

Two ways in, neither needs hardware.

The PC deck

python legacy/server.py

Opens 127.0.0.1:7710. Play music anywhere — Spotify, YouTube, a game — and it lights up on its own. Windows, because it captures WASAPI loopback and Windows media metadata.

Preview a panel you have not bought

sh tools/serve.sh

Compiles core/ to WASM and emulates any panel: grid size, level count, dot shape, illumination colour. Same C the firmware runs, so it is what the glass does rather than an impression of it.

Two corrections already made the hard way.

It must be the original ESP32, not the S3 — the S3 has no Bluetooth Classic, so no A2DP, so no audio from a phone. Espressif closed that request “Won't Do”.

The 8.8″ bar LCD does not fit a 1-DIN slot: about 217 mm wide against a 180 mm fascia. There is a colour panel that fits — a 4.58″ bar IPS at 118.8 × 41.57 mm, which maps onto the grid exactly at 192 × 64 logical dots times five — but it needs a parallel RGB bus the original ESP32 does not have, so colour is a two-chip build.

python3 tools/deckctl.py doctor

python3 tools/deckctl.py logs

The full guide is BUILD.md — shopping list with part numbers, wiring table, pairing, and the car install. The component survey is HARDWARE.md, where every claim is marked ✅ verified against a datasheet or listing, or ⚠️ not. Fitting is standard: an ISO 7736 cage and an ISO 10487 harness, so a home-built deck drops into any car that takes a normal head unit.

Two traps that each cost an evening. GPIO 34–39 on this chip are input-only and have no internal pull-ups — a button on one floats and reads as random presses, which looks exactly like a firmware bug. And ISO 10487 standardises the connector but not the pinout: A4 and A7 get swapped by manufacturers, so meter the harness before connecting anything.

When it does not work

A blank panel has six causes and one symptom. So the deck reports on itself.

This is the part hobby firmware usually skips, and skipping it is why people give up. There are three layers, each usable when the one above it is not.

1 — the panel

A four-stage boot self-test. Stage 1 is a pattern straight from the driver, before core/ is involved at all; stage 2 adds the output stage; stage 3 the font; stage 4 the subsystem table. Blank at stage 1 is hardware. Blank after stage 1 is software. That distinction is the whole reason it is staged.

2 — the serial line

One structured line per event, so a tool can parse it rather than needing a regexp per message. Health is four states, not a boolean: unknown means not tried yet, which is not failed — conflating them sends people hunting a Bluetooth bug on a deck nobody paired.

3 — the crash

A core dump written to flash survives the reboot, because the crash you care about happens in a car and not on the bench. deckctl coredump gives you the faulting task and a backtrace. A brownout reset says so plainly — in a vehicle that is cranking, not software.

Symptom-by-symptom table in DIAGNOSTICS.md, along with what to include in a bug report. On a dot-matrix display a photograph of the fault is worth more than any description of it.

How it holds together

One renderer, compiled twice. That is the whole architecture.

                     ┌── WASM ─────► browser preview (emulates any panel)
   core/  (C99) ─────┼── ESP32 ────► car firmware
                     └── Linux/Pi ─► firmware
   legacy/ (JS)  ───────────────────► the PC deck

A preview is only worth having if it is the same code as the firmware. If the preview were JavaScript and the firmware C, they would drift, and the preview would start lying about the hardware — at which point it is worse than useless, because you trust it.

So core/ is C99 with no libc, no libm, no allocation and no floating-point surprises. It ships its own trigonometry, because V8, glibc and an ESP32 do not agree to the last bit, and a dolphin should breach on the same frame everywhere. Screens write intensity levels 0–4; a per-target output stage decides what a panel shows — 16 greys, a 1-bit Bayer dither, or an RGB palette.

The one rule

core/ is verified against the JavaScript it was ported from.

sh tools/verify/run.sh

Both implementations render the same input and the framebuffers are diffed: fonts, every screen, text handling, metadata screens, the ocean, and every bundled movie decoded three separate ways. Change a screen's output on purpose and the diff fails — you update the expectation, you never delete the case.

This is not ceremony. It has caught a dolphin breaching one frame early, waterfall thresholds landing differently at double precision, and text dithering into mush on 1-bit panels — none of which was visible by eye.

And the deck runs on your computer

sh tools/sim/run.sh --gif deck.gif
python3 tools/sim/test_behaviour.py

The rule above covers the renderer. The layer above it — which screen is on, when the deck gives up and shows the clock, how a track change interrupts — is firmware, and it is the part most likely to be quietly wrong. So it compiles against stub drivers and runs here: the real deck_ui.c, in about a second, with twenty assertions about what it does. Checking “dolphins after twelve seconds of silence” on a bench costs fifteen seconds of standing in silence, per attempt.

It is not a simulation of the hardware, and TESTING.md says so explicitly: SPI timing, the Bluetooth stack and a supply that sags on crank fail on hardware and only on hardware. The bring-up checklist for those is on the same page.

What is in the repository

Eight directories, and it is worth knowing which one you are in.

PathWhat it is
legacy/The PC deck — a Python server that captures audio and metadata, and a JS faceplate that draws it. Moves slowly and deliberately, because it is what most people actually run
core/The portable renderer. C99, no libc, no libm, no allocation, its own trigonometry. Every screen lives here
preview/core/ compiled to WASM, with a harness that emulates any panel — grid, levels, dot shape, illumination
firmware/esp32/The car deck. A2DP audio, the analyser, both panel drivers, movies from flash, the self-test and the wheel-control learner. Compiles for both panels. Never flashed
tools/movies/The animation maker: a pure-Python 3D renderer, a GIF importer, the .dmv exporter and the flash packer
tools/verify/The differential suite. The reason anything here can be trusted
tools/sim/The firmware's own UI layer, compiled against stub drivers so the deck runs on a laptop — with twenty assertions about how it behaves over time
tools/media/Regenerates every picture on this page and in the README

Two files are worth opening before anything else: UI-SPEC.md, which explains why brightness alone must never carry meaning, and CLAUDE.md, which is the short version of everything the project learned the hard way.
